# 双地图打卡收尾与高德真实路径修复设计

## 1. 背景与结论

真机验证已经确认两个剩余问题：

- 高德地图 `16.21.0.2010` 的真实入口是“我的 → 足迹区域下的打卡点 → 开始打卡”。当前 Profile 仍按旧的“足迹 → 当前位置打卡”路径执行，并且高德部分节点会虚假返回 `ACTION_CLICK` 成功，页面实际不跳转。
- 百度地图 `21.18.50` 已能完成打卡，但成功页右上角“完成”没有自动点击，导致下一次打卡仍停留在上一次结果页。

本次只调整地图 UI Profile、动作标签、受限语义手势接入和 Worker 的收尾时序，不修改候选地点、事务存储、命令串行、重试次数或分屏创建策略。

## 2. 已确认行为

### 2.1 高德地图

高德按以下顺序执行：

```text
我的
  → 打卡点
  → 开始打卡
  → 等待 2000 毫秒
  → 再次点击开始打卡
  → 识别“打卡太频繁”为第一次点击已经生效的成功证据
```

第二次点击是固定业务步骤，不以第一次点击后是否出现“打卡太频繁”为前置条件。为了避免盲点，等待结束后仍需重新采集当前高德窗口，只在“开始打卡”仍是唯一、安全、可执行的语义目标时再次点击；如果页面已经变化，则回到正常 Profile 识别，不使用固定坐标。

### 2.2 百度地图

百度成功页必须返回 `SUCCESS + CLICK_DONE`。Worker 在回写成功结果前尝试点击右上角“完成”：

- 点击成功：记录清理动作，随后回写原成功结果。
- 点击失败：记录清理失败，但不把已经确认的打卡成功降级为失败。
- 下一条百度命令如果仍看到成功页，会再次尝试“完成”，不会直接执行新一次打卡。

## 3. 方案选择

采用“复用现有语义边界手势 + 显式收尾动作 + Worker 两阶段打卡状态”的方案。

### 3.1 选择理由

- 真机已经证明高德部分节点的 `ACTION_CLICK` 会返回成功但页面不跳转，单纯信任节点动作无法形成闭环。
- 现有语义边界手势已经具备唯一匹配、可见、启用、有效边界和窗口内中心点校验，可以复用于高德已验证版本。
- 高德的第二次点击属于跨 2000 毫秒的流程状态，不应隐藏在单次 Adapter 点击内部；由 Worker 显式保存阶段，日志和测试都更清晰。
- 百度“完成”属于成功后的页面清理，不能与“是否完成打卡”混为同一结果。

### 3.2 不采用的方案

- 不使用固定坐标或屏幕比例坐标：无法证明坐标仍对应当前语义目标。
- 不在 Adapter 内阻塞等待 2000 毫秒：会阻塞主线程并隐藏页面变化。
- 不把百度“完成”点击失败改写为打卡失败：这会否定已经出现的明确成功证据。
- 不继续沿用高德旧“我的足迹 → 当前位置打卡”路径：与当前真机页面结构不一致。

## 4. 架构与职责

### 4.1 `MapUiAction` 与动作标签

新增 `CLICK_DONE` 动作。

动作白名单调整为：

- 百度：
  - `CLICK_MINE` → “我的”
  - `CLICK_CHECK_IN_POINT` → “打卡点”
  - `CLICK_CHECK_IN` → “立即打卡”“立刻打卡”
  - `CLICK_DONE` → “完成”
- 高德：
  - `CLICK_MINE` → “我的”
  - `CLICK_CHECK_IN_POINT` → “打卡点”
  - `CLICK_CHECK_IN` → “开始打卡”

现有 `CLICK_FOOTPRINT` 可以保留以避免无关符号删除，但高德当前 Profile 不再决策该动作。

### 4.2 `AmapUiProfile`

Profile 使用 `hasActionableLabel` 判断交互目标，以支持节点点击和安全语义手势两种能力。

决策优先级为：

1. 登录、验证码等人工阻断。
2. “打卡太频繁”成功证据。
3. 其他明确成功或已打卡证据。
4. “开始打卡” → `CHECK_IN / CLICK_CHECK_IN`。
5. “打卡点” → `MINE / CLICK_CHECK_IN_POINT`。
6. “我的” → `HOME / CLICK_MINE`。
7. 其他页面 → `UNKNOWN / WAIT`。

“打卡太频繁”只在已经执行过本命令第一次“开始打卡”后，才由 Worker 作为成功终态接受；单独打开高德看到该文案不能凭空完成一条尚未提交的命令。

### 4.3 高德语义边界手势

`AmapMapAdapter` 在应用版本完全等于 `16.21.0.2010` 时，复用现有语义边界手势：

- 快照采集只把当前高德动作白名单标签作为候选。
- 节点 `ACTION_CLICK` 优先；节点点击返回 `false` 或找不到可执行节点时才使用手势。
- 手势目标必须唯一、启用、对用户可见、边界有效且中心点位于当前高德根窗口内。
- 每次动作最多提交一次手势。
- 版本不匹配时关闭手势能力。

高德和百度使用相同的安全选择器与手势分发器，但各自只读取自己的版本和标签白名单。

### 4.4 高德两次点击状态

Worker 为当前命令保存纯流程状态：

- `NONE`：尚未提交第一次“开始打卡”。
- `WAITING_SECOND_CLICK`：第一次动作已提交，等待 2000 毫秒。
- `SECOND_CLICK_SUBMITTED`：第二次动作已提交，等待 Profile 识别结果。

第一次 `CLICK_CHECK_IN` 成功提交后，Worker 进入 `WAITING_SECOND_CLICK`，使用主线程 Handler 延迟 `2000` 毫秒，不阻塞线程。

延迟结束后：

- 当前快照仍有唯一安全的“开始打卡”：提交第二次点击，进入 `SECOND_CLICK_SUBMITTED`。
- 页面已经变化：不盲点，直接按新快照继续 Profile 循环。
- 目标窗口在后台：保留阶段并走现有窗口恢复等待，恢复后继续当前阶段。

处于 `SECOND_CLICK_SUBMITTED` 后识别到“打卡太频繁”，命令返回成功，证据写明“第二次点击触发频率限制，第一次打卡已生效”。

### 4.5 百度成功页清理

`BaiduUiProfile` 识别“打卡成功 + 完成”时返回：

```text
page = SUCCESS
action = CLICK_DONE
evidence = 打卡成功，等待关闭结果页
```

Worker 在普通终态判断前识别 `SUCCESS + CLICK_DONE`：

1. 调用百度 Adapter 执行“完成”。
2. 记录动作结果。
3. 无论清理点击是否成功，均使用原 `SUCCESS` 回写命令。
4. 点击失败时在证据中增加 `cleanup=failed` 和失败原因。

这条特殊规则只适用于成功终态清理。其他终态仍沿用现有 `MapUiExecutionPolicy`。

## 5. 数据流

### 5.1 高德

```text
高德窗口根节点
  → AmapMapAdapter 采集可执行语义目标
  → AmapUiProfile 决策
  → Worker 执行“我的 / 打卡点 / 开始打卡”
  → 第一次开始打卡成功提交
  → Handler 延迟 2000 毫秒
  → 重新采集并安全提交第二次开始打卡
  → Profile 识别“打卡太频繁”
  → Worker 以成功结果回写
```

### 5.2 百度

```text
百度成功页
  → BaiduUiProfile 返回 SUCCESS + CLICK_DONE
  → Worker 尝试点击“完成”
  → 记录清理结果
  → 回写原成功结果
```

## 6. 错误处理与安全边界

- 高德第一次“开始打卡”动作提交失败：沿用现有动作失败结果，不进入第二阶段。
- 高德等待 2000 毫秒时窗口进入后台：保留命令和两阶段状态，不把后台等待计为动作失败。
- 高德第二次点击目标不存在或不安全：不使用坐标猜测，继续 Profile 识别并受现有超时限制。
- 高德第二次动作提交失败：返回明确动作失败，不伪造成功。
- 高德未进入第二阶段却出现“打卡太频繁”：不据此完成新命令，避免消费陈旧页面。
- 百度“完成”清理失败：打卡结果保持成功，日志保留失败原因，下一条百度命令优先重试清理。
- 所有语义手势仅对高德 `16.21.0.2010` 和百度 `21.18.50` 的精确版本开放。
- 不新增第三方依赖，不记录地点、地址或经纬度。

## 7. 测试与验收

### 7.1 单元测试

先写失败测试，再实现：

- 高德手势目标可驱动“我的”“打卡点”“开始打卡”决策。
- 高德不再选择旧 `CLICK_FOOTPRINT` 路径。
- 高德“打卡太频繁”能被 Profile 识别为明确证据。
- 两阶段策略只在第一次“开始打卡”成功后安排第二次点击。
- 第二次点击的延迟常量为 `2000L`。
- 第二阶段恢复时只有安全“开始打卡”目标才执行，不盲点。
- 未进入第二阶段时，“打卡太频繁”不能直接完成命令。
- 百度成功页返回 `SUCCESS + CLICK_DONE`。
- 百度“完成”动作标签只映射到百度。
- 百度清理成功和清理失败均保持原成功结果，失败原因进入证据。
- 原有阻断、版本限制、未知页计数和动作次数规则不变。

### 7.3 小米 14 真机验收

在已连接设备上安装同一构建产物，且不使用会抢占无障碍绑定的 `uiautomator`：

1. 确认 NearbyCheckIn 无障碍服务为 Enabled、Bound，Crashed services 为空。
2. 高德从首页完成“我的 → 打卡点 → 开始打卡 → 2000 毫秒 → 再次开始打卡”。
3. 日志出现“打卡太频繁”并将其记录为第一次点击生效的成功证据。
4. 百度完成打卡后自动点击右上角“完成”。
5. 再执行一轮百度命令时不需要人工关闭上一次结果页。
6. 两张地图均完成后，整笔事务进入 `COMPLETED`。
7. 地图窗口切到后台再恢复时，当前命令和高德两阶段状态保持不变。

## 8. 非目标

- 不修改候选地点、距离、停留、去重或巡航规则。
- 不修改命令租约、事务唯一事实来源或地图执行顺序。
- 不修改双窗口创建、后台恢复或主界面布局。
- 不适配高德、百度未验证版本。
- 不新增通用坐标点击、OCR 或图像识别。
